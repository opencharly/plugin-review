# 2026.255.1251 — fix(review): stream the completion and bound progress, not total generation

## Summary

Root fix for the validator reviews that die on the SAME turn with the same signature — on an endpoint that is demonstrably healthy and that DID deliver a complete turn-1 response:

```
plugin-review: attempt N/3 — provider=... model=... base_url=...
plugin-review: turn 1: 4 tool call(s)
plugin-review: attempt N failed: Post "https://.../chat/completions": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

This is a CLIENT-SIDE design defect, not an endpoint/egress/throttling fault.

### The RCA (verified from the source)

| # | Site | Fact |
|---|---|---|
| 1 | `review.go` const block | `defaultAttemptTimeout = 5 * time.Minute` |
| 2 | `llm.go` `newLLMClient` | `http: &http.Client{Timeout: timeout}` — ONE deadline covering an ENTIRE non-streaming request |
| 3 | `llm.go` `chat()` | POSTs `/chat/completions` with NO `stream: true` → response headers arrive only after the WHOLE generation |
| 4 | `review.go` `agentLoopOnce` | a 20-turn agentic loop, one `chat()` per turn |
| 5 | `review.go` `runAgentLoop` | 3 attempts, each re-running the WHOLE loop with the same timeout |

Turn 1 SUCCEEDS (small context). The harness then runs the 4 read-only tools and appends their output (the PR diff / thread / commits) as `tool` messages, so **turn 2's request carries a much larger context** — and because the call is non-streaming, the 5-minute timeout must cover the entire generation. It exceeds it → `awaiting headers`. Each attempt repeats the same sequence and fails at the same turn.

Contributing defects: (a) non-streaming + one whole-response deadline; (b) no custom `http.Transport` (default keep-alives: a reused idle POST after a long tool gap can hang to the deadline, and Go retries only idempotent requests); (c) unbounded tool-result size; (d) the retry re-runs the entire loop instead of the failed turn.

### The fixes

**(a) Stream the completion — bound PROGRESS, not total generation.** `chat()` now sends `stream: true` and consumes SSE (`scanSSE` + a `streamAccumulator` merging content deltas and index-keyed tool-call fragments). Two bounds replace the single wall clock: `AI_REVIEW_STREAM_IDLE_TIMEOUT` (silence between chunks, including the wait for the first one — default 3m) and `AI_REVIEW_ATTEMPT_TIMEOUT` (headers through the last chunk — default raised 5m → 15m). Handled: `[DONE]`, comment/keep-alive lines, EOF without `[DONE]`, multi-line `data:` events, provider `error` chunks. A provider/gateway that ignores `stream: true` and answers with a whole JSON body is still accepted (JSON fallback).

**(b) Explicit `http.Transport`.** `DisableKeepAlives: true` (every POST dials fresh — the loop is a handful of POSTs separated by minutes of local tool work), 30s `IdleConnTimeout`, `ResponseHeaderTimeout` = the whole-request bound, `ForceAttemptHTTP2`, bounded dial/TLS/ExpectContinue. `http.Client.Timeout` is now 0 and the bound is per-request, so a live streamed generation is never cut by a client-wide clock. The single re-issue policy lives in `chatTurn` (below): the review is read-only — all four tools are `gh api` GETs — so re-issuing a failed request is safe and deterministic.

**(c) Cap the tool-result payload.** Every tool result is truncated to `AI_REVIEW_TOOL_RESULT_MAX_BYTES` (default 64 KiB) before it becomes a `tool` message, with an explicit `[tool result truncated by the review harness: kept N of M bytes — the payload above is INCOMPLETE]` marker. This is the actual trigger of the context growth (diff up to 96 KiB, thread up to 100 comments x 24 KiB).

**(d) Retry the FAILED TURN, not the loop.** `chatTurn` re-issues the failing turn request (up to 3 attempts, 5s/10s backoff, context-aware) with the SAME conversation state. `runAgentLoop` re-runs a whole pass only when a COMPLETED pass produced no Verdict line, and a timeout-class failure returns the `inconclusive:` marker immediately instead of restarting the loop — a turn-2 timeout no longer re-pays turns 1..N.

**Adjacent correctness fix (same mechanism, found while capping).** `truncateStr`'s rune-boundary check was `json.Valid("\"" + b + "\"")`, which is FALSE for any payload containing a quote — i.e. for every real diff — so the boundary loop stripped back to the last JSON-string-safe position instead of merely dropping a partial rune. Measured with the new regression test: the OLD helper returns **42 bytes** for a 2048-byte budget; the fixed one returns **2048**. `utf8Valid` now uses `unicode/utf8`. (It only bites once the source payload exceeds the budget — `get_pr_diff` truncates at 96 KiB — but it silently gutted the diff whenever it did.)

**Docs.** README gains a "Review-engine bounds" section (the three knobs, their defaults, the rationale) and the `command:review` bullet now says streamed + per-turn retry.

### Notes for the reviewer

- The behavior change is deliberate and documented in the README: `AI_REVIEW_ATTEMPT_TIMEOUT`'s DEFAULT moves 300s → 900s, because it is no longer the bound that matters (the idle bound is). The knob keeps its name and precedence, so a runner that sets it explicitly is unaffected.
- `CHANGELOG/2026.254.1719.md` (PR #3) added the knob + the `inconclusive:` taxonomy for this same symptom; this PR removes the underlying trigger the taxonomy was classifying.
- The org workflow's CONSUMPTION of the `inconclusive:` marker is unchanged and lives in `opencharly/.github` (its own PR) — out of scope here.
- A provider that accepts `text/event-stream` but buffers the whole generation before flushing anything would trip the 3-minute idle bound; that class is reported as `inconclusive:` (never a BLOCK) and is tunable via `AI_REVIEW_STREAM_IDLE_TIMEOUT`.
