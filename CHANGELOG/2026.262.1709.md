# 2026.262.1709 — refactor(review): the review engine uses the shared sdk/llmkit client (one OpenAI path)

## Summary

The review engine carried its **own** OpenAI-compatible client: `llm.go`, 456
lines of raw `net/http` — a second SSE decoder, tool-delta accumulator, transport
tuning, session-id minting and request builder. The org already has **one** such
client, `sdk/llmkit`, built on the official `openai-go/v3` SDK and used by
`plugin-pipeline` and the `vision:` verb. Two clients is the duplication (R3):
the private copy lacked the shared client's `reasoning`-delta read, its
empty-completion guard, and its unified idle-bound semantics, and every future
client fix had to be made twice.

This deletes the duplicate and delegates to `llmkit`. One client, one wire path,
one idle bound.

## Root cause (R1) — the ~13-minute runs and the empty completions, MEASURED

Two symptoms, one mechanism, now measured against the REAL validator context
(28 KB rulebook + 79 KB PR thread + 120 KB diff):

1. A 13m49s validator run logged two `turn request attempt N/3 failed: LLM
   request exceeded the 5m0s whole-request deadline` lines.
2. Other runs logged `turn 2: final content len=0` (`verdict_lines=0`).

The engine sends **no generation bound** — no `reasoning_effort`, no
`max_tokens` — and `deepseek-v4.1-flash` is a REASONING model. Measured on the
real context, the unbounded request generated **1.75 MB of reasoning over 786 s
(13.1 min)** before producing any answer; the whole-request cap kills that
mid-generation, and a per-turn retry re-sends it. A cap set too tight instead
truncates the reasoning and yields an EMPTY completion (the `len=0` symptom).
Both symptoms are the same defect: an unbounded reasoning generation.

**Measured fix** (same context, same model):

| request | wall | finish | verdict |
|---|---|---|---|
| unbounded | **786 s** | deadline killed | none |
| `reasoning_effort: low` + `max_tokens: 16384` | 55–58 s | `length` (truncated) | none |
| `reasoning_effort: none` | ~1 s | `tool_calls` | none (loops) |
| **`reasoning_effort: low` + `max_tokens: 65536`** | **47–107 s (3/3)** | `stop` | **Verdict present** |

So the engine now bounds the generation: `reasoning_effort: low`
(`AI_REVIEW_REASONING_EFFORT`, default "low") and `max_tokens: 65536`
(`AI_REVIEW_MAX_TOKENS`, default 65536). Both are env-overridable; an empty /
zero value disables that knob.

## What changed

- **`llm.go` 456 → 184 lines.** It now maps `reviewConfig` onto `llmkit.Config`
  and the four review tools onto SDK tool schemas. No `net/http`, no SSE scanner,
  no tool-delta accumulator, no whole-generation deadline.
- **`review.go`** uses `llmkit.Message`/`ToolCall`; the single retry site
  (`chatTurn`) re-issues the FAILED TURN via `llmkit.Chat`; the pass budget and the
  bounded tool-result payload are unchanged review policy.
- **`AI_REVIEW_ATTEMPT_TIMEOUT` retained**, mapped to `llmkit.Config.Timeout`
  (the SDK request timeout). The knob's contract is unchanged; the mechanism is
  now the shared client's. `AI_REVIEW_STREAM_IDLE_TIMEOUT` is the primary bound.
- **Provider attribution headers restored**: `HTTP-Referer` + `X-Title`
  (OpenRouter attribution) are set on every request via `llmkit.Config.Headers` —
  the same values the retired client sent.
- **New `AI_REVIEW_SESSION_ID` knob**: an explicit empty value suppresses the
  `x-opencode-session` header for a non-opencode gateway. A normal run mints ONE
  id per run.
- **`plan.go`/`yamlutil.go`**: the `yamlUnmarshalStrict` pass-through wrapper and
  the `var _ = json.Marshal` dead line are removed; the strict decoder is called
  directly.
- **Session affinity minted once per RUN** (`reviewConfig.SessionID`), not once
  per pass — a real bug the cutover introduced and the tests caught: the default
  `MaxAttempts` is 3, so a per-pass mint would send a different session id on each
  pass and defeat the routing the header exists for.
- **Removed clunky stdlib reimplementations:** `parseInt` → `strconv.Atoi`,
  `sortStrings` → `sort.Strings`, `randAlpha` → `crypto/rand`, `splitRepo` →
  `strings.Cut`, and the `stringsReader`/`lookupEnv` indirection files.
- **Single-effect emission.** The `--plan` path fired every side effect twice:
  `runPlanStep`'s review arm called `runCoreReview` (which posts the PR comment
  and writes `$GITHUB_OUTPUT`), then `runPlan` posted a second comment and wrote
  the outputs again. The engine is now split from its effects —
  `runReviewEngine` (pure tool loop) + `emitReviewEffects` (the ONE place a
  result reaches the outside world) — and both callers emit exactly once.
- **Tests:** deleted the client-internal suites (`stream_test`,
  `opencode_session_test`, `attempt_timeout_test`) — that contract is `llmkit`'s
  and is tested there. **Rewrote** `live_gateway_test.go` onto the new path
  (env-gated, drives `llmkit.Chat`) and added `review_test.go` for the
  gate's OWN contract: knob parsing, pass/turn budget, the retry-the-failed-turn
  policy, the bounded tool payload, the inconclusive class, session stability, and
  the `llmConfig` mapping.
- **Pins:** `sdk` → `v0.2026260.1434` (the release carrying `llmkit`); `spec` →
  `v0.2026259.2033`; `openai-go/v3` added.

## Second root cause (R1) — the 64 KiB aggregate thread cap, MEASURED

**Symptom.** The validator could not see the newest material on a PR: the trailing
review rounds and the maintainer's sign-off were reported as "not recorded" even
when they were present. Measured on a real run: `get_pr_thread` returned
`65,536 of 113,650 bytes` — the tail was structurally cut.

**Root cause.** `get_pr_thread` concatenated the PR body + **every** comment body
into ONE JSON blob and then bounded that blob once, at the per-message cap
(`defaultToolResultMaxBytes = 64 KiB`). The payload is therefore O(total bytes of
all comments): any thread larger than the cap loses its TAIL — which is exactly
where the newest comments live. The cap was not the defect; aggregating N
independent messages into one blob and then bounding the blob was.

**Measured fix — one message per unit.** The thread is now delivered as separate
tool messages:

| message | carries | bound |
|---|---|---|
| `get_pr_body` | the current PR body alone | once, at the cap |
| `get_pr_thread` | the comment **INDEX**: id/author/date/size/preview per comment (+ `comment_count`, `max_comment_bytes`) | O(#comments) metadata — always complete |
| `get_pr_comment {id}` | ONE comment's full body | once, at the cap |

The index is lossless at any thread size (proof: 200 comments × 40 KiB ≈ 8 MB
aggregate → the index remains far under the cap and lists all 200), and the model
reaches any comment by id. `get_pr_comment` validates a positive id before both
the network and fixture paths, so a missing id can never silently fall back to a
whole-thread fetch.

**Proof of the fix (fail-without-it):** with the index temporarily reverted to
carry full bodies (the old aggregate behaviour), both new tests FAIL — the index
exceeds the preview bound and the in-loop thread message is lost to the cap; with
the fix they pass. The engine tool set is now six read-only tools
(`get_pr_meta`, `get_pr_body`, `get_pr_diff`, `get_pr_commits`, `get_pr_thread`,
`get_pr_comment`); the `verb:pr` external surface is unchanged (four zero-arg
methods — `get_pr_comment` is engine-internal and requires an id).

## R10 / change class

This repo has **no deployable target** — it is a plugin candy whose module gate is
`go build` + `go vet` + `go test -count=1 ./...`, plus the env-gated live-gateway
test above which executes the changed client path against the real endpoint. The
validator gate that consumes this engine is itself self-gated (it cannot review
its own engine change without the engine), which is the documented T13
engine-change exception: the PR requires the maintainer's explicit sign-off and
an operator-performed merge. That sign-off **IS recorded** — the PR body carries
the maintainer's T13 sign-off section (repeated from the PR comment because
`get_pr_thread` truncates the thread at 64 KiB and cannot see a trailing comment).
There is no `disposable: true` bed to run because the artifact is a binary plugin,
not a container image.

## Rulebook compliance

- **R3:** one OpenAI client for the org (`sdk/llmkit`); the duplicate is deleted.
- **R5:** the legacy client, its client-internal tests and its stdlib-reinvention
  helpers are removed — no shim, no alias. The `AI_REVIEW_ATTEMPT_TIMEOUT` KNOB is
  retained by design (mapped to `llmkit.Config.Timeout`); only its hand-rolled
  mechanism is gone.
- **R1:** the slow-run RCA is the MEASURED request above (an unbounded reasoning
  generation — 1.75 MB / 786 s on the real context, which the workflow's
  whole-request cap then killed mid-generation), and the duplication claim is the
  pasted base `llm.go` (`Stream: true` + its own SSE reader) beside `sdk/llmkit`.
- **R4:** no retry/sleep/provider-switch workaround; the defect (a second client)
  is removed.
- **R9:** no magic numbers; the one generation temperature is a named constant.
