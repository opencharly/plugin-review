## Summary

The review engine carried its **own** OpenAI-compatible client: `llm.go`, 456
lines of raw `net/http` — a second SSE decoder, tool-delta accumulator, transport
tuning, session-id minting and request builder. The org already has **one** such
client, `sdk/llmkit`, built on the official `openai-go/v3` SDK. Two clients is the
duplication (R3): the private copy lacked the shared client's `reasoning`-delta
read, its empty-completion guard, and its unified idle-bound semantics, and every
future client fix had to be made twice.

This deletes the duplicate and delegates to `llmkit`. **It also fixes a second,
independent defect**: the thread was delivered as one aggregate blob that the
64 KiB per-message cap truncated, hiding a PR's newest comments. Body, comment
index and each comment now travel as SEPARATE messages.

## Root cause 1 (R1) — the ~13-minute runs and the empty completions, MEASURED

Two symptoms, one mechanism, measured against the REAL validator context
(28 KB rulebook + 79 KB PR thread + 120 KB diff):

1. A 13m49s run logged two `turn request attempt N/3 failed: LLM request exceeded
   the 5m0s whole-request deadline` lines.
2. Other runs logged `turn 2: final content len=0` (`verdict_lines=0`).

The engine sent **no generation bound** — no `reasoning_effort`, no `max_tokens` —
and `deepseek-v4.1-flash` is a REASONING model. Measured on the real context, the
unbounded request generated **1.75 MB of reasoning over 786 s (13.1 min)** before
answering; a whole-request cap kills that mid-generation and the per-turn retry
re-sends it. A cap set too tight instead truncates the reasoning into an EMPTY
completion. Both symptoms are one defect: an unbounded reasoning generation.

**Measured fix** (same context/model):

| request | wall | finish | verdict |
|---|---|---|---|
| unbounded | **786 s** | deadline killed | none |
| `reasoning_effort: low` + `max_tokens: 16384` | 55–58 s | `length` (truncated) | none |
| `reasoning_effort: none` | ~1 s | `tool_calls` | none (loops) |
| **`reasoning_effort: low` + `max_tokens: 65536`** | **47–107 s (3/3)** | `stop` | **Verdict present** |

The engine defaults to `reasoning_effort: low` (`AI_REVIEW_REASONING_EFFORT`) and
`max_tokens: 65536` (`AI_REVIEW_MAX_TOKENS`); both are env-overridable, and an
empty/zero value disables that knob.

## Second root cause (R1) — the 64 KiB aggregate thread cap, MEASURED

**Symptom.** The validator could not see the newest material on a PR: trailing
review rounds and the maintainer sign-off were reported "not recorded" even when
present. Measured on a real run: `get_pr_thread` returned `65,536 of 113,650
bytes` — the tail was structurally cut.

**Root cause.** `get_pr_thread` concatenated the PR body + **every** comment body
into ONE JSON blob, then bounded that blob once, at the per-message cap
(`defaultToolResultMaxBytes = 64 KiB`). The payload is O(total bytes of all
comments), so any thread larger than the cap loses its TAIL — exactly where the
newest comments live. The cap was not the defect; aggregating N independent
messages into one blob and then bounding the blob was.

**Measured fix — one message per unit:**

| tool | carries | bound |
|---|---|---|
| `get_pr_body` | the current PR body alone | once, at the cap |
| `get_pr_thread` | the comment **INDEX**: id/author/date/size/preview per comment (+ `comment_count`, `max_comment_bytes`) | O(#comments) metadata — always complete |
| `get_pr_comment {id}` | ONE comment's full body | once, at the cap |

The index is lossless at any size because the comments request is **paginated**
(`gh api --paginate --slurp`, flattened across pages in `parseCommentIndex`) — a
plain `per_page=100` request would silently drop a >100-comment thread's newest
comments, the same tail-loss class. Proof: 200 comments × 40 KiB ≈ 8 MB aggregate
→ the index stays far under the cap and lists all 200; and the paginated
(array-of-pages) shape flattens to all 150 rows of a two-page 100+50 response.
The model reaches any comment by id. `get_pr_comment` validates a positive id before both the network
and fixture paths, so a missing id can never silently fall back to a whole-thread
fetch. This is the change that makes **body, index and each comment arrive as
separate messages**, so nothing is lost to the 64 KiB limit.
